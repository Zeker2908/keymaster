# ADR-013: Публикация JWKS

**Статус:** принят

## Контекст

Гейтвей принимает набор ключей целиком или не принимает вовсе: дубликат `kid` ломает весь
набор, максимум 50 ключей, нужен хотя бы один годный, любой не-2xx считается ошибкой (тогда
гейтвей остаётся на прошлом снимке). Ключ, не прошедший проверки (`kid`, `alg` из белого
списка, `use = sig`, согласованность `kty` и `alg`), пропускается молча.

## Решение

- `GET /jwks` без аутентификации, `Content-Type: application/json`,
  `Cache-Control: no-cache`, без редиректов (точный URL отвечает 200).
- В наборе ключи в состояниях PLANNED, ACTIVE и RETIRED на момент запроса
  (`listPublished(now)`). Порядок детерминирован (`publishAt`, затем `kid`).
- Поля JWK: `kty`, `kid`, `alg`, `use = sig` и параметры ключа (`n`, `e` для RSA;
  `crv`, `x`, `y` для EC). Только публичная часть (`toPublicJWKSet`), приватные поля
  отсутствуют, запрос не читает приватные колонки.
- Пустой набор или больше 50 ключей: ответ 503 `JWK_UNAVAILABLE` и запись уровня ERROR в
  лог. Набор не обрезается и не подменяется частичным.
- Путь именно `/jwks`: так он указывается в конфиге гейтвея.

## Последствия

- Любая ошибка видна гейтвею как не-2xx, и он остаётся на прошлом наборе.
- Первый опрос гейтвея на пустой базе не должен происходить до создания первого ключа.
  В стенде для этого нужна readiness-проверка «есть активный ключ подписи» (этап 6d).
- Корректность формата проверяется на трёх уровнях: unit-правила контракта, сквозной тест
  на Nimbus (токен, подписанный ключом из БД, проверяется ключом из `/jwks`) и контрактный
  тест на настоящем гейтвее.
- Дополнительная проверка длины `n` на «проводе» (ровно 256 байт, без ведущего нуля):
  парсер Nimbus ведущий ноль не показывает, а парсер гейтвея может его не принять.
