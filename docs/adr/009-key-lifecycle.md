# ADR-009: Жизненный цикл ключа подписи

**Статус:** принят

## Контекст

Гейтвей обновляет JWKS только по расписанию (сейчас раз в 300 с), токен с неизвестным
`kid` получает 401, отзыв ключа действует с задержкой до периода опроса. Любая ошибка в
ротации означает отказ в обслуживании без видимых ошибок на стороне `keymaster`.

## Решение

- Источник истины это временные метки: `publish_at`, `activate_at`, `retire_at`,
  `remove_at`, `revoked_at`. Состояние не хранится, а вычисляется чистой функцией
  `KeyLifecycle.stateAt(now)`. Интервалы полуоткрытые `[начало, конец)`.
- Состояния: PENDING (до публикации), PLANNED (опубликован, не подписывает), ACTIVE
  (подписывает), RETIRED (только проверка), REMOVED, REVOKED. В JWKS попадают PLANNED,
  ACTIVE и RETIRED, подписывает только ACTIVE.
- Правила: `activate_at ≥ publish_at + publishLead`, где `publishLead = 2 × poll`
  (запас на один сорвавшийся опрос); `remove_at ≥ retire_at + removeDelay`, где
  `removeDelay = maxAccessTtl + leeway + poll`. Первый ключ создаётся без запаса.
- Параметры `poll` и `leeway` обязаны совпадать с конфигом гейтвея (сейчас `poll = 300 с`,
  `leeway = 30 с`), `maxAccessTtl = 15 мин`. Пример: `publishLead = 600 с`,
  `removeDelay = 900 + 30 + 300 = 1230 с`.
- Единственный подписант гарантирует БД: `EXCLUDE USING gist` по диапазону
  `[activate_at, retire_at)`, без учёта алгоритма. Смежные диапазоны допустимы.
- Отзыв допустим в любой момент, в том числе до публикации (так отменяется запланированная
  ротация). При отзыве `retire_at ≤ GREATEST(revoked_at, activate_at)` (ограничение в БД),
  иначе отозванный ключ продолжал бы занимать слот подписанта.

## Последствия

- Корректность не зависит от планировщика: если он упадёт, состояние всё равно вычисляется
  по времени.
- Главный тест этапа это симуляция гейтвея (unit): при любой фазе опроса и одном сорвавшемся
  опросе снимок гейтвея содержит `kid` подписавшего ключа. Слагаемое `poll` в `removeDelay`
  это запас прочности (на задержку применения снимка и расхождение часов), а не часть
  строгой модели.
- Известное ограничение: отзыв активного ключа без заранее опубликованного резервного даёт
  паузу в выдаче работающих токенов до следующего опроса гейтвея. Резервный ключ реализуется
  на этапе 9.
