# ADR-008: Хранение приватных ключей подписи

**Статус:** принят

## Контекст

Приватный ключ подписи это самый ценный секрет сервиса: гейтвей доверяет любому токену,
подписанному им. Утечка дампа или бэкапа БД не должна раскрывать ключи.

## Решение

- Приватный ключ (PKCS#8) шифруется AES-256-GCM средствами JDK (`javax.crypto`), публичный
  хранится как X.509 SPKI без шифрования.
- Мастер-ключ: 32 байта в base64 из `KEYMASTER_MASTER_KEY`, в `%prod` без значения по
  умолчанию. Длина и формат проверяются при старте, приложение падает, не раскрывая
  значения.
- Nonce 12 байт, уникальный на каждую запись. В качестве AAD используется `kid`: шифртекст
  нельзя перенести на другую строку. Колонка `master_key_version` зарезервирована
  (сейчас 1).
- В расшифрованном виде ключ живёт в кэше по `kid` (несколько записей, короткий TTL):
  подписывать без ключа в памяти нельзя. Затирается только промежуточный `byte[]`.
- Приватные поля сущности не имеют публичных геттеров, запросы опубликованных ключей
  работают через проекции без приватных колонок. Ключи и мастер-ключ никогда не попадают
  в логи, `toString` и исключения.

## Последствия

- Утечка дампа БД без мастер-ключа ключи не раскрывает. Утечка процесса или обоих секретов
  раскрывает. Дампы памяти и core-файлы в проде отключаются.
- Потеря мастер-ключа означает невозможность подписывать старыми ключами: нужно создать
  новый ключ. Публичные ключи остаются в JWKS до `remove_at`, выданные токены доживают срок.
  Мастер-ключ хранится отдельно от бэкапов БД.
- Ротация мастер-ключа ручная и вне проекта. Возможный этап 12: карта «версия → ключ» в
  `KeyCipher`, перешифрование строк с устаревшей версией, отказ от старта при неизвестной
  версии.
- Путь развития: внешний сервис подписи (KMS, Vault Transit, HSM), где ключ в процесс не
  попадает.
