# ADR-010: Алгоритм подписи

**Статус:** принят

## Контекст

Контракт гейтвея: список разрешённых алгоритмов задаётся его конфигом, по умолчанию только
RS256, HS* и ключи `oct` отвергаются. Сначала рассматривался ES256, затем выбор остался за
RS256 (проверка на гейтвее дешёвая, сравнение k6 с Keycloak остаётся чистым). Позже набор
расширен.

## Решение

- Алгоритм хранится у каждого ключа (`alg`). Поддерживаются RS256, RS384, RS512, PS256,
  PS384, PS512 (RSA 2048) и ES256, ES384, ES512 (P-256, P-384, P-521).
- `keymaster.signing.algorithm` (по умолчанию RS256) задаёт алгоритм по умолчанию для
  новых ключей (при bootstrap и в админском эндпоинте этапа 9), а не алгоритм всего
  приложения. Токен подписывается алгоритмом активного ключа, а активный ключ определяется
  только расписанием (ADR-009).
- Список разрешённых алгоритмов в `keymaster` (`allowed-algorithms`, этап 9) зеркалит
  конфиг гейтвея: создание ключа и публикация в JWKS отвергают алгоритмы вне списка, иначе
  гейтвей молча пропустит такой ключ, и токены получат 401.
- Смена алгоритма это обычная ротация: ключи A (RS256) и B (ES256) одновременно в JWKS,
  подписывает один. Сначала алгоритм добавляется в конфиг гейтвея, потом создаётся ключ.
- Подпись формируется Nimbus (`RSASSASigner`, `ECDSASigner`): для ES формат `R||S`
  (64, 96 или 132 байта), JDK-овский DER руками не конвертируем. Координаты EC в JWK
  ровно по размеру кривой (32, 48, 66 байт), модуль RSA без ведущего нуля.

## Последствия

- Практически включать стоит только то, что есть в конфиге гейтвея (RS256, ES256). Каждый
  включённый алгоритм обязан проходить параметризованный набор тестов и контрактный тест на
  настоящем гейтвее.
- Проверка ES на гейтвее обычно дороже, чем у RSA-2048: сравнение нагрузки с Keycloak
  чисто только при одинаковом алгоритме.
- `CHECK` на `alg` в таблице ключей убран, допустимые значения проверяет enum `Algorithm`.

## Открытые вопросы

- Вернуть в БД `CHECK (alg IN (...))` со списком включённых алгоритмов, чтобы мусор не
  попадал в таблицу.
