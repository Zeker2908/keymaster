# ADR-014: Access-токен

**Статус:** принят (замер подписи внести после измерения)

## Контекст

Гейтвей не проверяет отзыв access-токенов, а роли в токене устаревают до следующего
refresh. Поэтому токен должен жить недолго. Токен читает только гейтвей, и вид принципала
он не использует.

## Решение

- TTL 10 минут (`keymaster.auth.access-token-ttl`), не больше `max-access-ttl` (15 мин):
  проверяется при старте. `max-access-ttl` это граница для расчёта ротации (ADR-009), а не
  само значение TTL.
- Claims: `sub` (UUID принципала), `roles` (отсортированный массив, возможно пустой),
  `iss`, `aud`, `iat`, `exp`, `jti`. Больше ничего: ни вида принципала, ни логина, ни
  данных профиля. Тест проверяет, что набор claims ровно такой.
- Заголовок: `alg` и `kid` активного ключа, `typ = JWT`.
- Подпись выполняется Nimbus ключом, который ACTIVE по `KeyLifecycle` на момент выпуска.
  Время берётся один раз на весь вызов: выбор ключа, `iat` и `exp` согласованы.
- Расшифрованный приватный ключ берётся из кэша по `kid` (ADR-008). Выбор активного ключа
  не зависит от `keymaster.signing.algorithm` (ADR-010).
- Ответ входа: `accessToken`, `refreshToken` (с этапа 6), `tokenType = Bearer`,
  `expiresIn` (секунды), заголовок `Cache-Control: no-store`. Это не OIDC.
- Вход `POST /auth/login` только для `kind = USER`. API-клиенты получают токен через
  `POST /auth/token` (этап 8), формат токена тот же.

## Последствия

- Отзыв и смена ролей действуют с задержкой до TTL токена. Новые права появляются при
  следующем refresh (роли перечитываются из БД).
- Если бэкенду когда-нибудь понадобится вид принципала, это правка двух сервисов (claim и
  заголовок `x-user-kind` на гейтвее), и делается она только по реальной потребности.
- Скорость подписи измеряется отдельно для каждого включённого алгоритма (подписей в
  секунду на ядро после прогрева) и записывается сюда.
