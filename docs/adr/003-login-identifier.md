# ADR-003: Идентификатор входа

**Статус:** принят

## Контекст

Почту подтверждать и использовать для восстановления доступа не планируется. Домен в
логине как фильтр бессмыслен без подтверждения почты: письма сервис не отправляет.

## Решение

- Вход по `login` формата `[a-z0-9._-]{3,32}`. Хранится в нижнем регистре, уникален
  (`UNIQUE` и `CHECK` в БД).
- При создании пользователя DTO отвергает недопустимые значения (в том числе заглавные
  буквы), а не молча приводит их к нижнему регистру. При входе введённый логин приводится
  к каноническому виду функцией `LoginNormalizer` (ADR-015).
- `sub` в токене это неизменяемый UUID принципала, а не логин. Логин можно будет менять,
  не ломая ссылки на пользователя (`x-user-id` у бэкендов остаётся прежним).
- Почты в модели нет.

## Последствия

- Восстановление пароля только через админа (сброс пароля). Никакого email-флоу.
- Если захочется «красивых» логинов с `@`, это остаётся конвенцией отображения: в БД и в
  `sub` она не нужна.
