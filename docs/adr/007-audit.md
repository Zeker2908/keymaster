# ADR-007: Аудит

**Статус:** принят

## Контекст

Нужен неизменяемый след административных изменений (пользователи, роли, ключи, позже
правила) без секретов, который невозможно потерять при сбое и нельзя подделать задним
числом.

## Решение

- Таблица `audit_log` только для добавления: триггеры в БД запрещают `UPDATE`, `DELETE`
  и `TRUNCATE`.
- Запись делает явный `AuditService.record(...)` в той же транзакции, что и изменение: нет
  изменения без следа и следа без изменения. Не используем аннотации и интерцепторы,
  триггеры БД, Envers и асинхронные события.
- `Actor(userId, requestId)` собирается в ресурсе из `RequestContext` один раз до цепочки и
  передаётся параметром вниз по сервисам. Для действий системы `userId = null`
  (bootstrap), `requestId = 'bootstrap'`.
- Поле `details` собирается вручную из белого списка простых значений для каждого действия,
  сущность целиком не сериализуется. Никогда: пароли, хэши, ключи, токены.
- `target_id` имеет тип `text`: цели бывают разных видов (UUID, `kid`, имя роли, версия
  правил). `actor_id` без внешнего ключа, журнал не зависит от остальной схемы.
- Пишем только административные изменения. Чтения, повторные идемпотентные операции без
  изменений, а также успешные и неудачные входы в `audit_log` не пишутся (входы идут в
  структурированный лог и метрики: поток управляется атакующим).

## Последствия

- Журнал нельзя чистить в тестах: используются уникальные логины и имена ролей, записи
  ищутся по `target_id`.
- Триггеры защищают от ошибок кода, но не от владельца схемы. Настоящая защита это
  отдельные роли БД (владелец миграций и пользователь приложения без DDL), этап 10.
- Эндпоинт чтения аудита (`GET /admin/audit` с фильтрами) добавим, когда понадобится.
